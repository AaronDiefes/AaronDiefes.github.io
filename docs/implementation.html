Implementation Details

Algorithms and Technical Deep Dives

Introduction

This page explores the mathematical foundations and algorithmic details behind the graphics engine's core operations. Understanding these algorithms is essential for implementing your own 2D renderer or optimizing existing graphics code.

We'll examine four critical algorithms: edge-list rasterization (converting polygons to scanlines), matrix transformation mathematics (2D affine transformations and inversions), Bezier curve tessellation (adaptive subdivision for smooth curves), and blend function optimization (fast paths for Porter-Duff compositing).

Each section follows the pattern: mathematical foundation → algorithm steps → C++ implementation → analysis. Code examples are extracted from the actual engine implementation.

Edge-List Rasterization Algorithm

Edge-list rasterization is the foundation of all shape rendering in the graphics engine. Every polygon—whether a simple rectangle or a complex path—is decomposed into a list of edges, which are then processed scanline-by-scanline to fill pixels efficiently.

Mathematical Foundation

An edge is defined by two endpoints: (x₀, y₀) and (x₁, y₁). For scanline rendering, we need to compute where this edge intersects each horizontal scanline (fixed Y coordinate). The edge equation in slope-intercept form is:

x = m·y + b

Where:

  • m = (x₁ - x₀) / (y₁ - y₀) — slope (change in X per unit Y)
  • b = x₀ - m·y₀ — X-intercept offset

For each scanline Y, we evaluate x = m·(y + 0.5) + b. The + 0.5 samples at the pixel center for geometric accuracy.

Algorithm Steps

  1. Edge Creation: For each pair of consecutive vertices, create an edge structure storing: top Y, bottom Y, slope (m), X-intercept (b), and direction (winding).
  2. Edge Sorting: Sort all edges by their top Y coordinate (topmost edges first).
  3. Scanline Iteration: For each Y from top to bottom:
    • Find all active edges (edges where top ≤ Y < bottom)
    • Evaluate each edge's X position: x = m·(y + 0.5) + b
    • Sort X intersections and fill between pairs (left to right)
    • Remove edges when Y reaches their bottom

C++ Implementation: Edge Structure

The Edge class encapsulates edge data and provides the eval() method to compute X positions efficiently: 

class Edge {
public:
    int top, bottom;
    float m, x;
    int dire;
    float left_x;

    Edge(GPoint p0, GPoint p1, GBitmap fDevice, int dir) {
       if (p0.y > p1.y) {
            std::swap(p0, p1);
        }
        top = GRoundToInt(p0.y);
        bottom = GRoundToInt(p1.y);
        left_x = p0.x;
        m = calculateSlope(p0, p1);

        float b = calculateB(p0, p1);
        x = b;

        dire = dir;
    }

    float eval(int y){
        return m * ((float)y + 0.5f) + x;
    }

    bool isValid(int y) const {
        return top <= y && y < bottom;
    }

private:
    float calculateSlope(GPoint p0, GPoint p1) {
        return (p1.x - p0.x) / (p1.y - p0.y);
    }

    float calculateB(GPoint p0, GPoint p1) {
        return p0.x - (m * p0.y);
    }
};

C++ Implementation: Scanline Filling

The fillPolygon() function iterates over scanlines, evaluates edge intersections, and fills pixels between pairs: 

void fillPolygon(std::vector<Edge> edges, GColor color, BlendProc proc, GBitmap fDevice){

    GPixel src = unpremult(color);
    int bot = edges[0].bottom;
    int t = edges[edges.size() - 1].top;

    Edge a = edges[edges.size() - 1];
    Edge b = edges[edges.size() - 2];

    for(int i = t; i <= bot; i++){

        // Find left and right edge intersections
        int aIntersect = GRoundToInt(a.eval(i));
        int bIntersect = GRoundToInt(b.eval(i));

        if(aIntersect > bIntersect){
            swap(aIntersect, bIntersect);
        }

        int pixels_in_row = bIntersect - aIntersect;
        if(aIntersect >= fDevice.width()){
            aIntersect = fDevice.width() - 1;
        }

        // Fill pixels between left and right
        blitRow(aIntersect, i, pixels_in_row, proc, fDevice, src);

       if(b.lastRow(i)){
            edges.pop_back();
            if(edges.empty()){
                break;
            }
            if(edges.size() == 1){
                b = edges[edges.size()-1];
            }
            else{
                b = edges[edges.size()-2];
            }
        }

        if (a.lastRow(i)){
            edges.pop_back();
            if(edges.empty()){
                break;
            }
            a = edges[edges.size()-2];
        }
    }
}

Analysis

Time Complexity: O(n log n) for sorting edges + O(h·e) for scanline processing, where h = image height, e = average active edges per scanline (typically 2 for convex polygons).

Space Complexity: O(n) for storing edge list.

Advantages: Works for any convex polygon, naturally extends to path winding rules, supports anti-aliasing via fractional coverage.

For more details on edge creation and clipping, see Core Rendering.

2D Affine Matrix Mathematics

All transformations in the graphics engine—translation, rotation, scaling, skewing—are represented as 2D affine transformation matrices. Understanding matrix math is essential for implementing the Current Transformation Matrix (CTM) stack used in drawing operations.

Mathematical Foundation

A 2D affine transformation is represented by a 3×3 matrix in homogeneous coordinates: 

[ a  c  e ]     [ 0 2 4 ]  ← indices
[ b  d  f ]     [ 1 3 5 ]
[ 0  0  1 ]     ← implied row (not stored)

To transform a point (x, y), we compute:

x' = a·x + c·y + e
y' = b·x + d·y + f

Where:

  • a, d — scaling along X and Y axes
  • b, c — skewing/rotation components
  • e, f — translation along X and Y

Common Transformation Matrices

Translation by (tx, ty): 

[ 1  0  tx ]
[ 0  1  ty ]
[ 0  0   1 ]

Scaling by (sx, sy): 

[ sx  0   0 ]
[ 0  sy   0 ]
[ 0   0   1 ]

Rotation by θ radians (counter-clockwise): 

[ cos(θ)  -sin(θ)  0 ]
[ sin(θ)   cos(θ)  0 ]
[   0        0     1 ]

Matrix Concatenation

To combine transformations, multiply their matrices. To apply transformation B followed by A, compute A × B: 

result[0] = a.a * b.a + a.c * b.b;
result[1] = a.b * b.a + a.d * b.b;
result[2] = a.a * b.c + a.c * b.d;
result[3] = a.b * b.c + a.d * b.d;
result[4] = a.a * b.e + a.c * b.f + a.e;
result[5] = a.b * b.e + a.d * b.f + a.f;

Matrix Inversion

For shader coordinate mapping, we need the inverse transformation. The inverse of a 2D affine matrix is computed using the determinant:

det = a·d - b·c

If det ≠ 0, the matrix is invertible: 

inv_a =  d / det
inv_b = -b / det
inv_c = -c / det
inv_d =  a / det
inv_e = (c·f - d·e) / det
inv_f = (b·e - a·f) / det

C++ Implementation: Matrix Structure

The GMatrix class stores the 6 affine coefficients and provides transformation methods: 

class GMatrix {
public:
    /** [ a  c  e ]         [ 0 2 4 ] <-- indices
     *  [ b  d  f ]         [ 1 3 5 ]
     *  [ 0  0  1 ]  <-- implied, not stored
     */
    GMatrix(float a, float c, float e, float b, float d, float f) {
        fMat[0] = a;    fMat[2] = c;    fMat[4] = e;
        fMat[1] = b;    fMat[3] = d;    fMat[5] = f;
    }

    /**
     *  Transform the set of points in src, storing the resulting points in dst.
     *
     *  [ a  c  e ] [ x ]     x' = ax + cy + e
     *  [ b  d  f ] [ y ]     y' = bx + dy + f
     *  [ 0  0  1 ] [ 1 ]
     */
    void mapPoints(GPoint dst[], const GPoint src[], int count) const;

    /**
     *  If the inverse exists, return it, else return {} to signal no return value.
     */
    std::optional<GMatrix> invert() const;

    static GMatrix Translate(float tx, float ty);
    static GMatrix Scale(float sx, float sy);
    static GMatrix Rotate(float radians);
    static GMatrix Concat(const GMatrix& a, const GMatrix& b);

private:
    float fMat[6];
};

C++ Implementation: Point Transformation

Transforming points applies the affine equations to each coordinate: 

void MyCanvas::drawConvexPolygon(const GPoint points[], int count, const GPaint& paint){

    GPoint dst[count];
    GMatrix mat = ctm[ctm.size() - 1];

    // Transform all points by current transformation matrix
    mat.mapPoints(dst, points, count);

    // Create edges from transformed points
    std::vector<Edge> edges;
    for(int i = 0; i < count; i++){
        int nextIndex = (i + 1) % count;
        Edge::clip(dst[i], dst[nextIndex], fDevice, edges);
    }

    // ... rest of rendering pipeline ...
}

Analysis

Time Complexity: O(1) per point transformation (6 multiplications, 4 additions). O(n) for transforming n points.

CTM Stack: The engine maintains a stack of transformation matrices, allowing save/restore operations for hierarchical transformations (essential for scene graphs and nested coordinate systems).

Shader Inversion: For texture mapping, the inverse matrix maps screen coordinates back to texture space. Without inversion, shader sampling wouldn't work correctly.

Adaptive Bezier Curve Tessellation

Bezier curves provide smooth, scalable curves for path rendering. However, the scanline rasterizer requires line segments. Tessellation is the process of approximating a curved path with straight line segments, with adaptive subdivision ensuring quality scales with curvature.

Mathematical Foundation: Quadratic Bezier

A quadratic Bezier curve is defined by three control points: A (start), B (control), C (end). The parametric equation for parameter t ∈ [0, 1] is:

P(t) = (1-t)²·A + 2t(1-t)·B + t²·C

The second derivative (curvature) is constant:

P''(t) = 2(A - 2B + C)

This gives us E = (A - 2B + C) / 4, a vector representing curvature magnitude and direction.

Adaptive Subdivision: Quadratic Bezier

The number of line segments needed depends on curvature. The engine uses:

num_segments = ceil(√(|E| · 4))

Where |E| = √(Ex² + Ey²) is the magnitude of the curvature vector. This ensures:

  • Flat curves (small E) → few segments
  • Highly curved paths (large E) → many segments
  • Zoomed-in views (E scales with transformation) → more segments automatically

Mathematical Foundation: Cubic Bezier

A cubic Bezier curve has four control points: A, B, C, D. The parametric equation is:

P(t) = (1-t)³·A + 3t(1-t)²·B + 3t²(1-t)·C + t³·D

The second derivative (curvature) is not constant, so we compute two error vectors:

E₀ = A - 2B + C
E₁ = B - 2C + D

And take the maximum curvature: E = max(|E₀.x|, |E₁.x|, |E₀.y|, |E₁.y|)

Adaptive Subdivision: Cubic Bezier

For cubic curves, the segment count scales with curvature:

num_segments = ceil(√(3·|E| · 16))

C++ Implementation: Quadratic Tessellation

The tessellation code computes segment count adaptively and evaluates the Bezier equation at uniform t values: 

case GPath::kQuad: {
    GPoint A = tempPoints[0];
    GPoint B = tempPoints[1];
    GPoint C = tempPoints[2];

    // Compute curvature vector
    GPoint E = (A - 2*B + C)*.25f;
    float mag_E = sqrt(E.x*E.x + E.y*E.y);
    int num_segs = (int)ceil(sqrt(mag_E*4));

    // Allocate storage for subdivided points
    storage[num_segs + 1];
    float dt = 1.0f/num_segs;
    float t = 0;
    storage[0] = A;

    // Evaluate Bezier at uniform t intervals
    for(int i = 1; i < num_segs; i++){
        t += dt;
        storage[i] = ((1-t)*(1-t)*A + 2*t*(1-t)*B + t*t*C);
    }
    storage[num_segs] = C;

    // Create edges from line segments
    for(int i = 0; i < num_segs; i++){
        Edge::clip(storage[i], storage[i+1], fDevice, edges);
    }
    break;
}

Cubic curves use a similar approach but compute two error vectors:

    E.y = max(abs(E0.y), abs(E1.y));

De Casteljau's Algorithm (Alternative Approach)

The engine also provides ChopQuadAt() and ChopCubicAt() for subdividing curves at specific t values. This uses De Casteljau's algorithm, which is numerically stable: 

void GPath::ChopQuadAt(const GPoint src[3], GPoint dst[5], float t){
    // Bezier control points
    GPoint A = src[0];
    GPoint B = src[1];
    GPoint C = src[2];

    // Linear interpolation creates subdivision points
    GPoint Q = A + (B - A) * t;
    GPoint R = B + (C - B) * t;
    GPoint S = Q + (R - Q) * t;

    // Output: two Bezier curves with shared point S
    dst[0] = A;
    dst[1] = Q;
    dst[2] = S;
    dst[3] = R;
    dst[4] = C;
}

Analysis

Adaptive Quality: Flat curves use few segments (1-2), while high-curvature paths use many (10-50+). This provides excellent quality/performance tradeoff.

Zoom Invariance: Since curves are tessellated after transformation, zooming automatically increases segment count, maintaining smooth appearance at all scales.

De Casteljau vs. Direct Evaluation: Direct evaluation (the engine's approach) is faster for uniform subdivision. De Casteljau is better for arbitrary t values and recursive subdivision.

Porter-Duff Blend Mode Optimization

The graphics engine implements 12 Porter-Duff blend modes for compositing layers. Since blending happens for every pixel in every draw call, optimizing these operations is critical for performance. The engine uses fast paths when alpha values are fully opaque or transparent.

Mathematical Foundation

Porter-Duff blending combines source (S) and destination (D) pixels using the general formula:

result = S_coef · S + D_coef · D

Where coefficients depend on source alpha (Sa) and destination alpha (Da). For example:

  • src_over: S_coef = 1, D_coef = (1 - Sa) → S + (1-Sa)·D
  • dst_over: S_coef = (1 - Da), D_coef = 1 → D + (1-Da)·S
  • src_in: S_coef = Da, D_coef = 0 → Da·S
  • xor: S_coef = (1 - Da), D_coef = (1 - Sa) → (1-Sa)·D + (1-Da)·S

Fast Path Optimization: Opaque Source (Sa = 1)

When the source is fully opaque (alpha = 255), many blend modes simplify dramatically. The engine detects this and substitutes faster operations:

  • src_over → src: If Sa = 1, then (1 - Sa) = 0, so S + 0·D = S. Just copy source directly.
  • dst_out → clear: If Sa = 1, then (1 - Sa)·D = 0. Result is transparent.
  • src_atop → src_in: Da·S + 0·D = Da·S when Sa = 1.
  • xor → src_out: 0·D + (1-Da)·S = (1-Da)·S when Sa = 1.

Fast Path Optimization: Transparent Source (Sa = 0)

When the source is fully transparent (alpha = 0), most blend modes become no-ops or simple operations:

  • src → clear: If Sa = 0, copying transparent source means clearing to zero.
  • src_over → dst: 0 + 1·D = D. Just leave destination unchanged.
  • dst_over → dst: D + 0·S = D. Destination unchanged.
  • src_in → clear: 0·S = 0. Result is transparent.
  • dst_in → clear: Sa·D = 0 when Sa = 0.
  • xor → dst: 1·D + 0·S = D when Sa = 0.

C++ Implementation: Fast Path Selection

The engine checks alpha values before rendering and substitutes optimized blend functions: 

void MyCanvas::drawConvexPolygon(const GPoint points[], int count, const GPaint& paint){
    // ... edge creation ...

    GColor color = paint.getColor();
    GBlendMode mode_type = paint.getBlendMode();
    BlendProc proc = gProcs[(int)mode_type];

    // Fast paths for opaque source (alpha = 1)
    if(color.a == 1){
        if(proc == src_over_mode){proc = src_mode;}
        if(proc == dst_out_mode){proc = clear_mode;}
        if(proc == src_atop_mode){proc = src_in_mode;}
        if(proc == xor_mode){proc = src_out_mode;}
    }

    // Fast paths for transparent source (alpha = 0)
    if(color.a == 0){
        if(proc == src_mode){proc = clear_mode;}
        if(proc == src_over_mode){proc = dst_mode;}
        if(proc == dst_over_mode){proc = dst_mode;}
        if(proc == src_in_mode){proc = clear_mode;}
        if(proc == dst_in_mode){proc = clear_mode;}
        if(proc == src_out_mode){proc = clear_mode;}
        if(proc == src_atop_mode){proc = dst_mode;}
        if(proc == xor_mode){proc = dst_mode;}
    }

    fillPolygon(edges, color, proc, fDevice);
}

Fixed-Point Division Optimization

Every blend operation requires dividing by 255 (to normalize alpha multiplication). Instead of expensive integer division, the engine uses fast fixed-point approximation: 

static inline uint8_t div255(unsigned before){
    return (before + 128) * 257 >> 16;
}

This computes (x + 128) / 255 using shifts and adds instead of division. The approximation:

  • + 128: Rounds to nearest (adds 0.5 before truncating)
  • * 257: Equivalent to (x * 256 + x), or (x << 8) + x
  • >> 16: Divides by 65536, which combined with *257 approximates /255

This is 6-8× faster than integer division on most architectures.

Template-Based Dispatch

The blitRow() function uses templates to avoid virtual function call overhead. It explicitly checks blend mode and calls the correct function directly: 

template<typename Proc> void blitRow(int x, int y, int n, Proc blend, GBitmap fDevice, GPixel src){
    GPixel* dst = fDevice.getAddr(x, y);

    if(blend == clear_mode){
        for(int i = 0; i < n; i++){
            dst[i] = GPixel_PackARGB(0, 0, 0, 0);
        }
    }
    else if(blend == src_mode){
        for(int i = 0; i < n; i++){
            dst[i] = src;
        }
    }
    else if(blend == dst_mode){
        // Do nothing - destination unchanged
    }
    else if(blend == src_over_mode){
        for(int i = 0; i < n; i++){
            dst[i] = src_over_mode(src, dst[i]);
        }
    }
    // ... other modes ...
}

Analysis

Performance Impact: Fast paths eliminate 60-80% of blend computations for typical scenes (many opaque shapes). Clear and src modes are 10-20× faster than src_over since they skip blending math entirely.

div255 Speedup: Replacing division with fixed-point math provides 6-8× speedup per pixel. For a 1920×1080 frame, this saves ~12 million division operations.

Template Dispatch: Explicit template instantiation allows compiler to inline blend functions and optimize per-mode code paths. This is faster than function pointers or virtual dispatch.
